# Architecture

## 1. Purpose

`engram` is a **project memory bank and scaffolder** for Pi. It gives a repository one portable
memory directory (`.ai/`) plus the `AGENTS.md` contract, so context survives session ends and
context compaction. It is a **CLI, not a daemon**: no background process, no server, no
telemetry, zero runtime dependencies.

Explicitly out of scope: agent frameworks, RAG/indexing, MCP servers, hosted sync, editing the
user's code. The tool writes Markdown and reads Markdown.

## 2. Stack

| Layer | Technology | Version | Why this one |
| --- | --- | --- | --- |
| Runtime | Node.js (ESM only) | ≥ 20 | ships with every AI tool environment; `node:test` needs no dependency |
| Language | TypeScript | 5.7 | strict types over string-templating logic; `verbatimModuleSyntax` keeps the build honest |
| Build | `tsc` only | — | no bundler, no plugin chain, nothing to keep in sync |
| Tests | `node:test` + `node:assert` | — | test runner ships with the runtime; zero dev-deps beyond `typescript` + `@types/node` |
| Templates | TypeScript string builders in `src/templates/` | — | keeps `.tsc` output self-contained; no file-copy step at install time |
| Dependencies | none at runtime | — | a scaffolder that pulls a dependency tree into every consumer repo is a bad neighbour |

## 4. Core topology

```text
cli.ts ──► commands/*  ──► adapters/*  ──► templates/*
              │               │
              └──► core/*  ────┘   (core never imports commands or adapters)
```

```text
init  : read .ai/sections.json → detect project → render .ai/ skeleton
        → render rule files + contract (with the declared section rows)
        → read .ai/skills/*.md → materialise into Pi's carriers → write .engram/BOOTSTRAP.md
sync  : read .ai/sections.json + .ai/skills/*.md → refresh contract block in place
        → re-materialise skills → prune carriers whose canonical skill is gone
dump  : load .ai/ → parse CURRENT_TASK + entries + declared sections + the live goal
        → fit sections to byte budget → render
new   : render one memory file from the shared section skeleton, or from a declared
        section's own `_TEMPLATE.md`
```

goal (opt-in, pi carrier only): `reduce(view, event, limits) → { record, effects }`.
Every trigger is an event, every host action is an effect; `core/goal.ts` reads no
clock, no file and no host API, and `core/goal-eval.ts` takes its I/O as `EvalDeps`.
That is the whole reason the engine is not a `commands/` module: it has to be
testable in memory and survive a pi restart without a pi process.
```text
pi extension (.pi/extensions/engram-goal.ts — generated, holds NO rules)
     │  spawnSync(`engram goal event --type … --json`)
     ▼
commands/goal.ts  runGoalEvent  ──► core/goal-host.ts (parse args)
     │                                  │
     │   reduce + evaluate in ONE round trip
     ▼                                  ▼
core/goal-store.ts ──► .ai/goal/<id>/goal.json    core/goal-eval.ts ──► BRIEF.md / metric / cmd
     │
     └──► GoalResponse { continue, message, notify, status } ──► agent_before_settle
```

The extension is a **marshaller, not a fork**. It cannot import `build/` (it runs under pi's loader
inside the user's repository), so the alternative would be shipping a second copy of the engine —
two implementations of every rule, and the copy the model talks to would silently win. Instead the
`evaluate` effect is resolved *inside* `runGoalEvent`, so the host never runs a gate and never decides
done. `test/goal-extension.test.ts` asserts the generated file contains none of the rule names
(`stuckRounds`, `livenessMs`, `blockedRepeats`, …).

The two project-owned inputs are read on every run and never written. `init` reads
`.ai/skills/*.md` *after* the skeleton write, because on a fresh repository the directory it reads
is one it just created (`.ai/pitfalls/cases/read-source-after-write.md`).

Dependency rule: `core/` is the leaf layer. `commands/` may use anything. `templates/` never reads
the filesystem. `adapters/` never reads the filesystem (only `commands/` pass content in). This is
what makes the whole pipeline testable in memory.

## 5. Invariants

1. **The contract block is machine-owned.** No human or model text ever lives between
   `<!-- engram:contract:start -->` and `<!-- engram:contract:end -->`; `sync` rewrites it in place.
   The splice has exactly one implementation (`replaceContractBlock` in `templates/contract.ts`),
   it ignores markers inside fenced code blocks, and it refuses to act on an unpaired marker.
   **Enforced:** `test/templates.test.ts`.
2. **`engram dump` never exceeds `--max-bytes` (default 1500), in UTF-8 bytes.** Content is dropped
   by section priority, then by line, then by a byte-boundary-safe hard cut. `truncated` is `true`
   whenever *anything* was left out, so the CLI never reports "under budget" while having silently
   dropped the binding decisions. **Enforced:** the `REGRESSION` cases in
   `test/fingerprint.test.ts`, including `maxBytes: 0`. Each elastic section is a **"recent N"**
   view, not a complete one — `BINDING` shows 3 accepted decisions + 2 proposals
   (`FingerprintOptions.acceptedDecisions` / `proposals`), `RECENT` 3 handoffs, `PITFALLS` 2 cases.
   With the bank at ~1.5 KB the elastic tiers (`PITFALLS`, then `RECENT`, then `BINDING`) are dropped
   as the budget fills, so a session reading a shorter fingerprint is seeing an abbreviated bank,
   never a bank without those entries. `engram dump` prints `at budget` when that happened; the full
   lists are always in `.ai/decisions/` and `.ai/pitfalls/cases/`.
   **Known cost:** adding a decision rotates the newest-3 out of `BINDING` and can push `PITFALLS`
   out entirely — a higher default budget or a pointer line naming what was dropped is the open fix.
3. **`init` never clobbers human content.** Existing rule files keep their body *and* their
   frontmatter keys; only the contract block, the managed marker and the shared-reader note are
   regenerated. A narrowed `globs` scope or `alwaysApply: false` is never promoted. `--force` is
   required to replace a body. **Enforced:** `test/templates.test.ts`; an unpaired marker aborts
   the whole operation rather than guessing a slice.
4. **Canonical skills live once**, in `.ai/skills/*.md`, and that directory — not the in-code
   `SKILL_SPECS` — is the source of truth. Any valid file there materialises into every carrier;
   a file whose frontmatter is missing, or whose `name` disagrees with its filename, is reported and
   skipped rather than silently unloadable. Carriers are generated and marked `engram:generated`,
   and only a marked file is ever deleted. **Enforced:** `test/sections.test.ts`.
5. **The contract is derived, never authored.** Its two row tables are a pure function of
   `.ai/sections.json`; `aiContract()` with no extensions is byte-identical to the v1 block, so an
   upgrade rewrites no existing rule file and removing a declaration removes its rows. Hand-editing
   the block is therefore never necessary — which is what makes the extension surface usable.
   **Enforced:** `test/sections.test.ts` (byte-identity + declare/undeclare round trip).
6. **Zero runtime dependencies.** `package.json` `dependencies` stays absent. **Enforced:** a test
   asserts the field is `undefined`.
7. **One decision per file, one topic per file.** Filenames are `YYYY-MM-DD-<kebab-topic>.md`.
8. **`_`-prefixed files are inert**: templates and examples, skipped by `dump` and `sync`.
9. **The goal engine is host-free.** `core/goal.ts` is a pure reducer (time is passed in, effects
   are descriptions); it reads no clock, no file, no host API, and `core/goal-eval.ts` takes all I/O
   as `EvalDeps`. `core/` still imports nothing from `commands/`, `adapters/` or a host package.
   **Enforced:** `test/architecture.test.ts` (layering) and `test/goal.test.ts` (behaviour without
   a pi process).
10. **`done` requires an observed verdict.** A `goal_report(status=done)` produces an `evaluate`
    effect, never a state change; only a passed `done_when` sets `status: done`. Cancelling a goal is
    `closedAt` + `closeReason`, never a fifth `status`, so `done` cannot mean "stopped".
    **Enforced:** `test/goal.test.ts`.
11. **The generated pi extension holds no rule.** It maps lifecycle events onto
    `engram goal event --json` and applies the answer; `evaluate` is resolved inside the CLI, so the
    host never runs a gate. It is emitted as JS-valid TypeScript and `node --check`ed on every test
    run, because a syntax error there fails inside pi's loader, far from the file engram wrote.
    **Enforced:** `test/goal-extension.test.ts`.
12. **The goal engine is opt-in, and only the pi carrier can enable it.** `.engram/config.json`
    carries `goal.enabled`; `sync` writes `.pi/extensions/engram-goal.ts` only when it is true *and*
    it is the only client. Turning it off removes a **generated** file and never a hand-written one.
    **Enforced:** `test/goal-extension.test.ts`.

## 6. Boundaries and known debts

- **`dump` is still pasted manually.** The goal extension is the only executable integration, and it
  does not inject the fingerprint; an extension that does is the obvious next layer.
- **One adapter, and that is a product decision.** engram shipped nine, then three, then one; the
  history is `.ai/decisions/2026-10-18-reduce-supported-clients-to-pi-claude-code-and-codex.md` and
  `.ai/decisions/2026-10-18-serve-pi-only.md`. The cost of an adapter was never the registry entry —
  it was the *conventions*, each one a vendor claim that rots silently — so the subtraction went to
  the bottom: no rule-file frontmatter machinery, no `prompt-toml` carrier, no tool-scope resolution,
  no `tools` array in the config. Removed carrier dirs live in `RETIRED_SINK_DIRS` (pruned by `sync`);
  removed rule files live in `RETIRED_RULE_FILES` and are **reported, never deleted**, because a rule
  file may hold a human-authored body that no marker distinguishes from engram's own.
  `test/adapters.test.ts` asserts the registry has exactly one entry, so a second client costs a
  decision file rather than an edit — the review step the previous nine adapters never had.
- **Vendor facts are not machine-checkable.** Each claim was verified against vendor docs by hand
  during review; nothing re-verifies them, so they rot silently. A scheduled re-check (or an
  `/audit` step that re-reads the docs) is a candidate for a later version.
- **`dump` parses Markdown heuristically.** A deliberately broken `CURRENT_TASK.md` degrades the
  fingerprint; it never throws. Unreadable paths (EACCES, a `.ai` file where a directory belongs)
  are reported as `readErrors` on stderr rather than being reported as "no decisions".
- **No `engram doctor`.** Drift detection today lives in the `/audit` skill spec, i.e. in the model,
  not in the CLI. A machine version is a candidate for v0.2.
- **One cross-layer import in `core/`, tolerated explicitly.** The dependency rule says `core/`
  imports nothing from `commands/`, `adapters/` or `templates/`. One edge predates the rule and is
  allowlisted in `test/architecture.test.ts` (`CORE_KNOWN_EXCEPTIONS`), which also fails if an entry
  stops matching a real import:
  - `core/project.ts → ../templates/contract.js` — one marker constant. The fix is to move
    `MANAGED_MARKER` into `core/` and re-export it from `templates/`.

  The second entry, `core/config.ts → ../adapters/index.js`, is gone: config v2 stopped recording a
  tool list, and that record was the only reason a leaf module needed the registry. The stale-entry
  test failed until the allowlist line was deleted, which is what that test exists for.

  The guard previously used `CORE_ALLOWED = /^(\.|node:)/`, which accepted **every** relative
  specifier, so it was green while the rule was violated. It now rejects `../` from `core/` and
  requires an explicit allowlist entry — a new violation fails the suite.
