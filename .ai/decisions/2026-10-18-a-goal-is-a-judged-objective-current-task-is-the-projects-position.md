# 目标与 CURRENT_TASK：一个是「判据」，一个是「处境」

**Status:** ✅ ACCEPTED · **Date:** 2026-10-18 · **Deciders:** zeroicey

## 先撤销一个错误的说法（这一节是这份文件存在的理由）

这份决策的第一版写的是：

> **一个 goal 是 CURRENT_TASK.md 的一个「切片」，绝不是它的副本。**

用户直接否掉了这个说法：

> 我们定的目标是一个总目标、一个宏观的目标，比如研究我们要把这个模型的 mAP 训练到多少值以上。
> 那为什么你这里说的是一个「项目切片」一样的东西？……我还是没有太理解 current task 和目标之间的关系。

**他是对的，我把轴搞错了。** 「切片」描述的是**大小**，而大小根本不是区分这两者的维度：

- 我参照的是**本仓库的用法**——这里每个 goal 只做一个里程碑（L2 是一个里程碑），于是我把**本地习惯**
  当成了**语义**。
- 引擎对目标的大小**没有任何要求**。它只要求一件事：这个目标能被机器判定。所以
  `{"kind":"metric","file":"out/eval.json","path":"eval.mAP","op":">=","value":0.85}` 是**一等公民**，
  `metric` 这个形状存在的理由就是它。

保留下来仍然正确的只有一半：**同一个事实不要写两遍**。错的是把它说成「小」。

## 真正的区分轴：判据 vs 处境

| | 一个 goal | `.ai/CURRENT_TASK.md` |
| --- | --- | --- |
| 是什么 | **一个带机器判据的目标**（`done_when`） | **这场追求的处境**：项目现在是什么状态 |
| 结束条件 | 引擎观测到判据成立 → `done` | 永不「完成」；只被更新 |
| 大小 | **任意**。宏观（跑几周的 mAP）和微观（`npm test`）同等合法 | 不适用 |
| 谁写 | `goal.json` 只由引擎写；`BRIEF.md` 由模型写 | 人 + 结算时的 agent |
| 身份 | 有 id（由目标文字生成的 slug） | 没有 id，也不是某个 goal 的别名 |
| 形态 | `BRIEF.md`（目标 + `done_when` + 不是目标的东西）、`TASKS.md`（本目标的清单） | Status / Goal / 里程碑清单 / Code state / Blockers / Next action |

两者可以**在同一句话上重合**——这本身不是冲突。冲突只发生在两种情况：它们**互相矛盾**，或者**计划被
写了两遍**。

## 决策：怎么权衡（这就是可以照做的规则）

1. **目标只声明一次，由 goal 声明。** `CURRENT_TASK.md` 可以用一句话说项目的长期抱负（`dump` 里渲染为
   `project:`），但**不得重复 goal 的判据，也不得重复它的计划**。
2. **计划在任何时刻只存在一个地方**：有 goal 打开时，计划是那个 goal 的 `TASKS.md`；没有 goal 时，计划是
   `CURRENT_TASK.md` 的 `Next action`。
3. **只有 `TASKS.md` 可以被判据当作 gate。** `CURRENT_TASK.md` 的清单是**路线图**，永远不做 gate——
   让机器判定里程碑会把项目方向冻成测试。
4. **结算时两边都写回。** `goal.json` 记录这一轮做了什么；`CURRENT_TASK.md` 记录**项目因此发生了什么变化**
   （勾掉它服务的那一项、更新 next action、更新 blockers）。
5. **一个 goal 可以服务任意一个清单条目**——研究、开发、或者一个既不是研究也不是开发的「任务表」条目。
   引擎不关心这件事属于哪一类，只要求它有判据。
6. **一张 goal 一次只开一个**（见 `2026-10-18-scope-the-goal-to-the-project-with-a-single-baton-and-no-wor.md`）。
   这是规则 2 之所以无歧义的前提。

## 粒度：宏观 goal 还是里程碑式 goal

引擎两种都支持，代价不同，**这是使用者的选择，不是设计的偏好**：

- **宏观 goal**（`goal new "把 mAP 训练到 0.85"` + `--metric`）：判据就是那个数。子工作放 `TASKS.md`，
  处境放 `CURRENT_TASK.md`，中途用 `progress` / `wait` / `blocked` 推进，判据成立才 `done`。
  得到：一次连续的追求，跨多个 session、多次 handoff。失去：**没有嵌套**——所以两周里想顺手开一个小 goal
  会被拒绝。
- **里程碑式 goal**：每个里程碑有自己的判据和一次干净的关闭，检查点更密、每个阶段都有可见的 `done`。
  代价是每个阶段一次 `goal new`。

设计时的设想是前者：等待/长任务那两份决策讨论的就是「一次训练跑 7–16 小时」。

## 后果

- `dump` 里两个词已经分开：`project:`（项目处境）与 `GOAL / run:`（当前这一轮 + 判据）。之前两行都叫 `goal`，
  一个全新 session 读到会以为有两个任务、且不知道做哪个。
- 剩下的重复风险是**散文层面**的：如果有人把 `CURRENT_TASK.md` 的 `## Goal` 改写成描述「当前这一轮」，
  两者又在说同一件事。测试看不见这个，属于 `/audit` 的职责。

## Revisit when

- 一个项目真的需要同时推进多个目标——那时规则 2 和 6 都要重新设计。
- `CURRENT_TASK.md` 出现任何**机器读取**的字段：那会把它从「散文」变成「引擎输入」。
